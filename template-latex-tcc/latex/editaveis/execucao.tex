\chapter[Execução do Experimento]{Execução do Experimento}

\section{Visão geral da execução}

Este capítulo descreve a execução do experimento conduzido neste trabalho, detalhando as etapas realizadas para operacionalizar 
o planejamento apresentado no capítulo anterior. Enquanto o capítulo anterior apresentou o planejamento experimental, 
incluindo objetivo, questão de pesquisa, variáveis, hipóteses, desenho experimental, instrumentação e ameaças à validade, 
este capítulo detalha como o experimento foi operacionalizado na prática.

A execução envolveu a preparação da base experimental, a recuperação dos trechos de código a partir do dataset MLCQ, 
a construção dos prompts utilizados nos modelos de linguagem, a configuração do ambiente do SonarQube, a 
aplicação dos tratamentos experimentais e a organização dos resultados para posterior análise estatística.

O experimento avaliou sete tratamentos: SonarQube, ChatGPT com prompt zero-shot, ChatGPT com prompt few-shot, Claude com prompt zero-shot, 
Claude com prompt few-shot, DeepSeek com prompt zero-shot e DeepSeek com prompt few-shot. Cada modelo de linguagem associado a uma versão 
específica de prompt foi considerado um tratamento distinto.


\section{Preparação da base experimental}

A preparação da base experimental teve início com a análise do dataset MLCQ, apresentado por \citeonline{MadeyskiLewowski2020MLCQ}, que reúne amostras de código Java previamente 
classificadas quanto à presença ou ausência de diferentes tipos de code smells, utilizado como fonte dos exemplos de código e dos respectivos vereditos de referência. 
Essa análise inicial teve como objetivo compreender a estrutura dos dados disponíveis, identificar os campos necessários para 
a execução do experimento e verificar a quantidade de registros aptos para uso. 

No MLCQ, o dataset é composto por respostas de avaliadores, de modo que um mesmo \textit{sample} pode possuir mais de uma resposta associada. A inspeção inicial considerou 14.739 registros desse tipo. Após o processo de filtragem, no qual foram removidos registros inválidos (sem \textit{sample} válido ou com links de origem quebrados/inacessíveis) e respostas duplicadas para o mesmo \textit{sample}, permaneceram 8.711 registros válidos para execução. Como cada trecho tende a aparecer em dois registros, um para cada smell aplicável ao tipo do elemento analisado, os 8.711 registros correspondem a 4.364 \textit{samples} únicos: em 4.347 casos houve duas avaliações por \textit{sample} (totalizando 8.694 registros) e, em 17 casos, houve apenas uma avaliação, resultando no total final de 8.711 registros. Esses \textit{samples} estão distribuídos em 522 repositórios. Esses números foram utilizados para caracterizar a base experimental e orientar as etapas seguintes de recuperação dos trechos e construção dos instrumentos de avaliação.




O MLCQ fornece metadados associados a cada amostra, como o identificador do trecho, o repositório de origem, o tipo do elemento analisado, 
as linhas de código correspondentes e o veredito final atribuído à presença ou ausência de determinado code smell. Com base nesses metadados, 
os trechos de código foram recuperados e organizados para que pudessem ser submetidos tanto aos modelos de linguagem quanto ao SonarQube.

Foram considerados quatro tipos de code smells: Blob/God Class, Data Class, Feature Envy e Long Method. Os dois primeiros estão associados 
à análise de classes, enquanto Feature Envy e Long Method estão associados à análise de métodos ou funções. Essa distinção foi utilizada para 
definir quais perguntas seriam feitas aos modelos de linguagem e quais regras seriam aplicadas no SonarQube.


\section{Recuperação dos trechos de código}

Após a análise inicial da base, foi realizada a recuperação dos trechos de código correspondentes a cada sample. 
Essa etapa foi necessária porque o experimento não utilizou os arquivos completos em que o trecho se encontra, mas apenas os trechos
indicados pelos metadados do MLCQ.

Para cada amostra, foram utilizados os metadados disponíveis no dataset para localizar o arquivo de origem e selecionar 
as linhas correspondentes ao trecho avaliado. Dessa forma, cada sample passou a ser representado pelo fragmento de código 
efetivamente associado ao veredito de referência do MLCQ.

Essa decisão foi importante para manter a equivalência entre os tratamentos experimentais. Como as LLMs receberiam 
apenas o trecho de código no prompt, o SonarQube também deveria analisar uma entrada equivalente. Por isso, os arquivos 
submetidos ao SonarQube foram preparados contendo apenas os trechos identificados na análise de cada sample, evitando que a ferramenta 
tivesse acesso a um contexto maior do que aquele fornecido aos modelos de linguagem.

Com isso, buscou-se garantir que todos os tratamentos analisassem, na medida do possível, a mesma entrada experimental. 
Essa padronização foi adotada para reduzir diferenças decorrentes do volume de contexto disponível e permitir uma comparação mais controlada 
entre os resultados produzidos pelas LLMs e pela ferramenta de análise estática.

\section{Construção dos prompts}

Para cada tipo de trecho recuperado, foram criadas duas versões de prompt: uma versão zero-shot e uma versão few-shot. 
A versão zero-shot foi construída sem explicações conceituais ou exemplos prévios sobre os code smells. 
Nesse caso, o modelo recebia apenas o trecho de código e a pergunta sobre a presença ou ausência dos smells correspondentes ao tipo de elemento analisado.

Quando o trecho analisado correspondia a uma classe, o prompt questionava se o código apresentava Blob/God Class e/ou Data Class. 
Quando o trecho correspondia a um método ou função, o prompt questionava se o código apresentava Long Method e/ou Feature Envy.

A versão few-shot, por sua vez, incluiu informações adicionais sobre os smells avaliados. 
Nessa versão, o prompt apresentava uma definição conceitual dos code smells pertinentes ao tipo de elemento analisado e incluía 
um exemplo conceitual de como esses smells poderiam se manifestar. Assim, para trechos de classe, o prompt continha definições e 
exemplos relacionados a Blob/God Class e Data Class. Para trechos de método ou função, o prompt continha definições e exemplos relacionados a Long Method e Feature Envy.

Os prompts utilizados no experimento são documentados no Apêndice~\ref{ap:prompts-execucao} por meio de exemplos representativos de cada configuração. Para a reprodução integral dos prompts, recomenda-se consultar o arquivo \textit{Script-Api-LLMs/prompts.json} disponível no repositório de execução do trabalho \cite{repositorio_tcc}. Essa organização permite explicitar a estrutura textual empregada em cada tratamento.


\section{Preparação do ambiente com SonarQube}

Além da avaliação com modelos de linguagem, o experimento incluiu um tratamento baseado no SonarQube, empregado como plataforma de análise estática. Para isso, foi criada uma máquina virtual com 12 GB de memória RAM, utilizada para instalar e configurar o ambiente local de execução da ferramenta, bem como os componentes necessários para o processamento dos trechos de código recuperados do MLCQ.

Como o SonarQube, por padrão, não identifica code smells seguindo diretamente a nomenclatura do catálogo de \citeonline{Fowler1999}, 
foi desenvolvido um plugin específico para detectar os quatro smells considerados neste trabalho: Blob/God Class, Data Class, Feature Envy e Long Method.

Para Blob/God Class, Data Class e Feature Envy, foram utilizadas estratégias de detecção baseadas nas métricas descritas 
por \citeonline{Lanza2006}. Essas estratégias também são utilizadas 
como referência em outras ferramentas e estudos de detecção de code smells.

No caso do Long Method, embora ferramentas como SonarQube e PMD possuam regras relacionadas ao tamanho de métodos, 
essas regras geralmente se baseiam apenas na métrica LOC, isto é, na quantidade de linhas de código. 
Como não há consenso único sobre o limiar mais adequado para caracterizar esse smell, optou-se por utilizar a regra 
descrita por \citeonline{ArcelliFontana2016}. 
Nesse estudo, os autores utilizaram técnicas de aprendizado de máquina para derivar regras de detecção de smells. 
Para Long Method, foi adotada a regra que combina LOC e complexidade ciclomática: LOC(method) > 79 e CYCLO > 9.

O plugin foi implementado como um projeto Java, gerenciado com Maven, e continha regras específicas para os smells Long Method, Data Class, Feature Envy e Blob/God Class. Cada regra foi responsável por percorrer a estrutura do código Java analisado e registrar uma \textit{issue} quando os critérios definidos para o respectivo smell eram atendidos.

O desenvolvimento do plugin envolveu a criação de uma classe principal responsável por registrar as extensões no SonarQube, uma definição do repositório de regras customizadas e classes específicas para cada regra de detecção. Após a implementação, o plugin foi compilado com Maven, gerando um arquivo \textit{.jar}. Esse arquivo foi copiado para o diretório \textit{extensions/plugins} da instalação local do SonarQube.

Após a habilitação, as regras customizadas passaram a estar disponíveis na interface do SonarQube e puderam ser utilizadas durante a análise dos arquivos Java gerados a partir do dataset. As regras foram identificadas por chaves como \textit{custom-java-smells:long-method}, \textit{custom-java-smells:data-class}, \textit{custom-java-smells:feature-envy} e \textit{custom-java-smells:blob-god-class}. Assim, o SonarQube funcionou como plataforma de análise estática, enquanto o plugin customizado foi responsável pela operacionalização dos critérios de detecção dos smells avaliados.

As evidências visuais da configuração do projeto e da ativação das regras customizadas foram reunidas no Apêndice~\ref{ap:sonar-evidencias}, de modo a concentrar as capturas de tela do SonarQube em um espaço próprio de documentação.

Como o SonarQube realiza análise estática sobre arquivos de código-fonte, os trechos do dataset foram previamente convertidos em arquivos Java individuais. Cada arquivo recebeu no nome o identificador original da amostra, como \textit{Snippet\_3698323.java}, permitindo associar posteriormente cada \textit{issue} detectada ao respectivo \textit{sample\_id}.

As \textit{issues} geradas foram exportadas para o arquivo \textit{sonar\_snippet\_issues.jsonl} e, em seguida, convertidas para uma representação simplificada em \textit{sonar\_sample\_smells.jsonl}, contendo o \textit{sample\_id}, o arquivo analisado e o smell detectado. Essa etapa permitiu comparar a saída do SonarQube com as respostas produzidas pelos modelos de linguagem, conforme os artefatos disponibilizados no repositório de execução do trabalho na pasta sonar-trechos. \cite{repositorio_tcc}.

\section{Desenho de execução e aleatorização dos tratamentos}

Após a preparação da base, dos prompts e do ambiente de análise estática, a execução do experimento seguiu o desenho Randomized Complete Block Design, 
conforme descrito por \citeonline{Wohlin:2012:ESE:2349018}. Nesse desenho, todos os tratamentos são aplicados a cada objeto experimental, mas a ordem de aplicação é aleatorizada.

Neste trabalho, cada sample ou trecho de código foi considerado um objeto experimental. Para cada objeto, os sete tratamentos foram aplicados: 
SonarQube, ChatGPT zero-shot, ChatGPT few-shot, Claude zero-shot, Claude few-shot, DeepSeek zero-shot e DeepSeek few-shot.

A ordem de aplicação dos tratamentos foi definida aleatoriamente para cada sample. Assim, antes da análise de um determinado trecho, 
era sorteada a sequência em que os tratamentos seriam executados. Após todos os tratamentos serem aplicados ao mesmo sample, 
o experimento avançava para o próximo trecho, no qual uma nova ordem aleatória era definida.

Esse procedimento foi adotado para reduzir possíveis efeitos relacionados à ordem de execução dos tratamentos ou resquícios de dados mantidos em memória. 
Embora os tratamentos automatizados não apresentem os mesmos efeitos de fadiga ou aprendizagem observados em 
experimentos com participantes humanos, a aleatorização contribui para manter o rigor experimental e evitar que algum 
tratamento seja sistematicamente favorecido ou prejudicado por sua posição na sequência de execução.

\section{Execução do Experimento}

A execução dos tratamentos experimentais foi realizada de forma integrada, contemplando tanto os modelos de linguagem quanto o SonarQube. 
Para cada \textit{sample}, os tratamentos definidos no experimento foram aplicados conforme a ordem estabelecida pelo processo de aleatorização descrito anteriormente.

Os resultados gerados por cada tratamento foram armazenados em arquivos no formato JSONL, organizados a partir do notebook de execução e dos artefatos mantidos no repositório do trabalho \cite{repositorio_tcc}. Além dos arquivos de saída das LLMs e do SonarQube, 
foi mantido um arquivo de log de execução contendo os registros de início, término, duração, tratamento aplicado, tipo de tratamento, 
código de retorno e status da execução. Esse log permitiu rastrear a execução de cada tratamento para cada \textit{sample}.

O período total de execução do experimento foi identificado a partir dos logs registrados durante o experimento. Com base nesses registros, 
o experimento teve início em 21/06/2026 às 01:08:47 e término em 23/06/2026 às 13:39:59, 
totalizando uma duração cronológica de 2 dias, 12 horas, 31 minutos e 12 segundos.

Além da duração cronológica, foi calculado o tempo acumulado de execução. 
Essa medida representa o tempo total consumido pelas execuções registradas, enquanto a duração cronológica representa o intervalo real 
entre a primeira e a última execução. O tempo acumulado total foi de 214.957,84 segundos, equivalente a aproximadamente 3.582,63 minutos ou 59,71 horas.

\section{Organização dos resultados}

Após a execução dos tratamentos, os resultados foram organizados em uma base única de análise. Essa base integrou as respostas dos modelos de linguagem, 
os resultados do SonarQube, os metadados dos prompts e os vereditos de referência do MLCQ, todos consolidados a partir dos arquivos produzidos no repositório de execução do trabalho \cite{repositorio_tcc}.

Cada registro da base final correspondeu à avaliação de um tratamento sobre um determinado sample e smell. 
Para cada linha, foram armazenadas informações como identificador da amostra, tipo do elemento analisado, smell avaliado, 
tratamento aplicado, versão do prompt quando aplicável, predição produzida e veredito de referência.

No caso das LLMs, as respostas textuais foram convertidas em rótulos padronizados, indicando presença ou ausência do smell. 
Esse processo de padronização foi necessário para permitir a comparação direta entre as predições dos modelos e o ground truth. 
No caso do SonarQube, os resultados da análise estática também foram convertidos para o mesmo formato de rótulo.
