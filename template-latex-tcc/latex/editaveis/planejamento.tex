\section{Definição do Escopo do Experimento}

\subsection{Objetivo}

A literatura tem destacado que a detecção automática de
code smells ainda enfrenta limitações importantes, especialmente quando baseada
exclusivamente em regras sintáticas fixas, como ocorre em ferramentas tradicionais de
análise estática. Paralelamente, modelos de linguagem de grande porte (LLMs) têm sido
crescentemente empregados em tarefas de compreensão e geração de código, indicando
um potencial para apoiar atividades relacionadas à garantia da qualidade de software.

Nesse contexto, o objetivo deste experimento é investigar empiricamente o papel de sistemas baseados em IA na garantia da qualidade de software, 
por meio da avaliação da capacidade de modelos de linguagem (LLMs) em detectar code smells um tipo de anomalia 
frequentemente associada à degradação da qualidade do código.

\subsection{Trabalhos Relacionados}

Durante a definição da abordagem empírica adotada neste Trabalho de Conclusão de Curso, foram selecionados estudos
metodológicos em Engenharia de Software que serviram de referência para o planejamento e a condução do experimento. 

A principal influência para a estruturação do método foi o livro de \citeonline{Wohlin:2012:ESE:2349018}, que sistematiza o processo de 
experimentação em Engenharia de Software, descrevendo etapas, papéis, ameaças à validade e formas de análise dos 
dados. As diretrizes propostas pelos autores foram utilizadas como base para o planejamento do experimento, definição das 
variáveis, seleção dos sujeitos e elaboração dos instrumentos de coleta e análise. 

Além disso, o trabalho dialoga com a classificação de métodos de pesquisa em Engenharia de Software apresentada por 
\citeonline{Basili1994}, que distingue, entre outros, o método empírico como aquele voltado à investigação do comportamento humano 
em contextos reais de desenvolvimento.  

Por fim, as contribuições de \citeonline{Wohlin:2012:ESE:2349018} sobre investigação empírica em Engenharia de Software foram consideradas 
como apoio, especialmente no que diz respeito à caracterização de estudos observacionais e experimentais e à 
discussão sobre validade interna, externa e de construção. Em conjunto, esses trabalhos forneceram a estrutura conceitual e 
metodológico que orientou a condução do experimento no trabalho.

No que se refere a base de qualidade adotada, foram considerados os modelos clássicos de \citeonline{McCall1977} e 
\citeonline{boehm1978characteristics}, que organizaram fatores e subfatores de qualidade e propuseram uma estrutura hierárquica para análise 
de produtos de software. Esses referenciais fornecem uma base conceitual para relacionar propriedades de projeto e 
implementação a atributos de qualidade interna e de manutenibilidade, servindo como fundamento para a discussão sobre 
como code smells podem impactar a qualidade do produto ao longo de seu ciclo de vida.

A partir desses modelos, normas posteriores como a \citeonline{ISOIEC9126} e a \citeonline{ISOIEC25010} consolidaram e refinaram a taxonomia de 
características de qualidade, destacando, entre outras, a analisabilidade. Neste trabalho, tais modelos 
foram utilizados como pano de fundo conceitual para enquadrar os code smells como indícios de degradação da qualidade interna 
e para justificar o foco na detecção e análise desses problemas de projeto.

Para o estudo de code smells, o trabalho de \citeonline{Fowler1999} foi crucial para a aplicação desenvolvida neste estudo, 
pois forneceu o referencial conceitual e o catálogo original de code smells que orientaram a seleção dos 
tipos de problemas de projeto analisados. A partir dessa base, foi possível alinhar a detecção e a interpretação 
dos \textit{smells} aos modelos de qualidade adotados.

Partindo para a vertente de detecção automática de code smells, o estudo de \citeonline{MadeyskiLewowski2020MLCQ} foi 
fundamental, pois apresentou o \textit{dataset} MLCQ, que reúne trechos de código Java anotados manualmente quanto à presença 
de diferentes \textit{code smells}. Esse \textit{dataset} serve como base para a avaliação comparativa das abordagens de detecção 
adotadas no experimento, fornecendo rótulos humanos que funcionam como referência  para medir a eficácia 
das técnicas avaliadas. Em complemento, o estudo de \citeonline{Fontana2016} descreve outra base de dados, que foi bastante utilizada nos estudos, com características 
semelhantes ao MLCQ, que também foi considerada como referência para a seleção dos code smells analisados e para a 
definição das avaliações utilizadas neste trabalho.

Para o uso de LLMs na análise de código, o trabalho de \cite{Abtahi2025LLMStaticAnalysis, Tkachuk2025RefactoringGAI} foi 
relevante, pois explorou o potencial de modelos de linguagem para tarefas de análise estática e refatoração de código. 
Esses estudos demonstraram a viabilidade de empregar LLMs para compreender e avaliar trechos de código, fornecendo 
ideias sobre como esses modelos podem ser aplicados na detecção de \textit{code smells}. As abordagens metodológicas 
e os resultados apresentados nesses trabalhos serviram como base para a formulação das hipóteses e o desenho experimental 
adotado neste estudo.

Em síntese, os trabalhos aqui discutidos forneceram a base conceitual e empírica para a definição do problema, a escolha dos
\textit{code smells} de interesse, a seleção dos \textit{datasets} e a adoção de LLMs como tratamento experimental. A partir desse
referencial, a próxima seção apresenta o planejamento do experimento, detalhando o contexto, as variáveis, os tratamentos
e os procedimentos de coleta e análise de dados adotados neste estudo.



\section{Planejamento}

\subsection{Contexto}

O experimento será conduzido no contexto dos projetos \textit{open-source} que compõem o
dataset MLCQ, apresentado por \citeonline{MadeyskiLewowski2020MLCQ}. O MLCQ reúne trechos de código
extraídos de sistemas Java reais e anotados manualmente por desenvolvedores quanto à presença,
tipo e severidade de \textit{code smells}, funcionando como referência (rótulo humano) para a
avaliação dos tratamentos experimentais.

A escolha do MLCQ como fonte de dados experimentais fundamenta-se em evidências 
identificadas na revisão estruturada da literatura. Diversos estudos recentes têm utilizado o 
MLCQ em experimentos envolvendo detecção automática de \textit{code smells} 
\cite{Kovacevic2022AutomaticDetection,Ho2025EnseSmells,Sandouka2025CrossLanguage}. 
Essa adoção decorre do fato de que o dataset foi construído com a participação de desenvolvedores profissionais, 
cujas anotações foram validadas por múltiplos revisores, assegurando confiabilidade e reduzindo vieses individuais, 
além de abranger uma grande diversidade de sistemas reais.

\textbf{Sujeito do experimento:} o sujeito não é um participante humano, mas sim o próprio
dataset MLCQ, entendido como a fonte empírica sobre a qual os tratamentos serão aplicados.

\textbf{População:} a população é composta pelos 792 projetos Java provenientes do
dataset MLCQ.

\textbf{Amostra:} a amostra é formada pelos aproximadamente 15.000 trechos de código-fonte individualmente anotados
no MLCQ. Cada trecho corresponde a uma instância candidata de code smell, definida pelos
metadados do dataset, incluindo: \textit{repository}, \textit{commit hash}, \textit{path}, \textit{start line},
\textit{end line}, \textit{smell type}, \textit{severity} e \textit{type}.

Para a execução do experimento, cada trecho de código será reconstruído a partir dos metadados fornecidos pelo dataset
(\textit{repository}, \textit{commit hash}, \textit{path}, \textit{start line} e \textit{end line}),
garantindo a fidelidade ao código original existente no momento da anotação. As abordagens de detecção serão então aplicadas sobre o mesmo conjunto de trechos de código-fonte,
permitindo comparações pareadas entre abordagens distintas de detecção de \textit{code smells}.

Como os tratamentos envolvem modelos fechados (LLMs), preserva-se a versão do modelo,
as configurações utilizadas e os prompts empregados, de forma a garantir reprodutibilidade.
Além disso, o experimento não envolve sujeitos humanos, ocorrendo exclusivamente no
ambiente técnico composto pelo dataset, repositórios GitHub e ferramentas automatizadas.

\subsection{Variáveis do Experimento}

As variáveis são definidas conforme terminologia de \citeonline{Wohlin:2012:ESE:2349018}.

\subsubsection*{Fator Experimental}
O experimento possui um único fator: \textbf{Analisabilidade aplicada à detecção de code smells}.
O fator possui cinco níveis (tratamentos), correspondentes às ferramentas avaliadas:

\begin{enumerate}
    \item \textbf{SonarQube} (versão Community Build Release 25.11.0.114957), abordagem baseada em regras estáticas;
    \item \textbf{ChatGPT} (GPT-5.1), LLM da OpenAI;
    \item \textbf{Gemini} (Gemini 3 pro), LLM do Google;
    \item \textbf{Copilot} (GPT-5), LLM da Microsoft;
    \item \textbf{DeepSeek} (DeepSeek-V3.2).
\end{enumerate}

\subsubsection*{Variável Independente}
A variável independente é composta pelos \textbf{trechos de código} que constituem os objetos experimentais.
Onde os tratamentos serão então aplicados sobre o mesmo conjunto de trechos de código-fonte.

\subsubsection*{Variáveis Dependentes}
A variável dependente é quantitativa e corresponde à \textbf{quantidade de code smells identificados por projeto para cada tratamento}.


Com base nessa variável primária, serão calculadas as seguintes métricas estatísticas:

\begin{itemize}
    \item \textbf{Mediana} do número de code smells detectados;
    \item \textbf{Variância} e \textbf{desvio padrão} das distribuições;
\end{itemize}

\subsection{Formulação das hipóteses}

As hipóteses foram definidas de forma a permitir a comparação estatística entre os
tratamentos, considerando a distribuição da quantidade de \textit{code smells} identificados
por projeto. Seja $W_i$ a mediana da distribuição de \textit{code smells} identificados pelo
tratamento $i$, onde $i \in \{1,2,3,4,5\}$ representa, respectivamente:
SonarQube, ChatGPT, Gemini, Copilot e DeepSeek.

A hipótese nula estabelece que todos os tratamentos produzem distribuições equivalentes.
A hipótese alternativa assume que ao menos um tratamento difere significativamente
dos demais.

\begin{itemize}
    \item \textbf{Hipótese Nula ($H_{0}$):} 
    \[
        W_{1} = W_{2} = W_{3} = W_{4} = W_{5}
    \]
    Isto é, não há diferença estatisticamente significativa entre as medianas das quantidades
    de \textit{code smells} identificados pelos diferentes tratamentos.

    \item \textbf{Hipótese Alternativa ($H_{1}$):}
    \[
        \exists\, i,j \mid W_{i} \neq W_{j}
    \]
    Ou seja, ao menos um tratamento identifica uma quantidade de \textit{code smells}
    estatisticamente diferente dos demais.
\end{itemize}

\subsection{Desenho do Experimento}

O experimento caracteriza-se como um \textbf{experimento orientado à tecnologia}
(\textit{technology-oriented experiment}), conforme classificação apresentada por
\citeonline{Wohlin:2012:ESE:2349018}. Nesse tipo de estudo, não há participação de sujeitos humanos;
o foco está na avaliação comparativa de técnicas, ferramentas ou algoritmos aplicados
a artefatos de software.

O desenho experimental adotado é o \textbf{Completely Randomized Design}, 
no qual os tratamentos são aplicados em ordem aleatória sobre cada objeto experimental.
Nesse tipo de design, todos os objetos pertencem a um único grupo, e a aleatorização 
garante que cada tratamento seja aplicado em condições equivalentes, reduzindo vieses 
decorrentes de ordem ou de efeitos sistemáticos de execução.


\subsection{Teste de Hipóteses}

Para avaliar se há diferença estatisticamente significativa entre os tratamentos 
na detecção de code smells, será utilizado o teste não paramétrico \textbf{Kruskal--Wallis}, 
conforme recomendado por \citeonline{Wohlin:2012:ESE:2349018} para experimentos com um único fator e mais de dois 
tratamentos.

O teste Kruskal--Wallis constitui uma alternativa não paramétrica à análise de variância 
(ANOVA) de um fator, sendo apropriado quando os dados são derivados de distribuições 
assimétricas, possuem outliers ou representam medições ordinais ou baseadas em rankings, 
como é o caso dos valores agregados por projeto (medianas) no presente experimento. 

\subsection{Instrumentação}

A instrumentação se refere às ferramentas e artefatos que serão utilizados para a
execução do experimento. Serão utilizados os seguintes instrumentos para apoiar a execução do experimento:

\begin{itemize}
    \item \textbf{Dataset MLCQ}\footnote{Disponível em: \href{https://doi.org/10.5281/zenodo.3590101}{https://doi.org/10.5281/zenodo.3590101}. Acesso em: 6 dez. 2025.}: o MLCQ é um conjunto 
    de dados de código Java anotado manualmente por desenvolvedores quanto à presença, tipo e severidade de \textit{code smells}. 
    No experimento, o MLCQ será utilizado como fonte dos metadados de cada instância de \textit{code smell}. Cada linha do dataset 
    corresponde a uma anotação individual, identificada pelo campo \textit{id}, associada a um revisor específico (\textit{reviewer\_id}) e 
    a uma amostra de código (\textit{sample\_id}). Os campos \textit{smell} e \textit{severity} registram, respectivamente, o tipo de \textit{code smell} 
    identificado e a severidade atribuída, enquanto \textit{review\_timestamp} armazena a data e hora da anotação. 
    
    O tipo de elemento de código avaliado, por exemplo, função, método ou classe é descrito em \textit{type}, e o nome qualificado desse elemento é registrado em \textit{code\_name}. 
    A origem do artefato é caracterizada pelos campos \textit{repository} (repositório Git de origem), \textit{commit\_hash} (identificador do 
    \textit{commit} em que o trecho foi anotado) e \textit{path} (caminho do arquivo dentro do repositório), enquanto a região de interesse é delimitada 
    por \textit{start\_line} e \textit{end\_line}. O campo \textit{link} fornece a URL para visualização do arquivo e das linhas correspondentes na 
    interface web do GitHub, e \textit{is\_from\_industry\_relevant\_project} indica se o projeto é considerado relevante para a indústria. Em conjunto, 
    esses metadados serão utilizados para localizar o arquivo completo, reconstruir o contexto do trecho anotado e empregar o rótulo humano como 
    referência na avaliação dos tratamentos experimentais.


    \item \textbf{Git}\footnote{Disponível em: \href{https://git-scm.com/}{https://git-scm.com/}. Acesso em: 6 dez. 2025.}: o Git é um sistema de controle de versão distribuído amplamente
    utilizado para gerenciamento de código-fonte. No experimento, o Git será empregado
    para clonar os repositórios necessários, realizar \textit{checkout} em commits
    específicos indicados no MLCQ e assegurar a integridade e consistência dos trechos
    de código reconstruídos.
    
    \item \textbf{GitHub}\footnote{Disponível em: \href{https://github.com/}{https://github.com/}. Acesso em: 6 dez. 2025.}: o GitHub é uma plataforma de hospedagem e versionamento de
    código baseada em Git, amplamente utilizada para projetos open-source. A partir
    das informações fornecidas pelo MLCQ, os repositórios originais serão acessados 
    (via \textit{clone} local ou API do GitHub) para obtenção dos arquivos 
    correspondentes a cada \textit{commit}. Os trechos de código analisados no 
    experimento serão extraídos com base nas linhas inicial e final indicadas no dataset.
    
    \item \textbf{Scripts em Python}: A linguagem Python\footnote{Documentação oficial do Python disponível em: \href{https://www.python.org/}{https://www.python.org/}. Acesso em: 6 dez. 2025.}
    será responsável por automatizar a reconstrução dos trechos a partir do MLCQ e do GitHub, pela execução dos tratamentos 
    (SonarQube e LLMs) e pela comparação das respostas com a rotulação humana, gerando as variáveis dependentes (acerto, falso positivo, falso negativo).
    
    \item \textbf{SonarQube}\footnote{Disponível em: \href{https://www.sonarqube.org/}{https://www.sonarqube.org/}. Acesso em: 6 dez. 2025.}: ferramenta de Análise Estática configurada com o \textit{rule set} padrão para Java, utilizada como um dos tratamentos de 
    detecção de \textit{code smells}.
    
     \item \textbf{ChatGPT}\footnote{Documentação em: \href{https://platform.openai.com/docs}{https://platform.openai.com/docs}. Acesso em: 6 dez. 2025.}:
    o ChatGPT é um modelo de linguagem de grande porte desenvolvido pela OpenAI,
    baseado na arquitetura \textit{transformer}. Ele é capaz de interpretar instruções
    em linguagem natural e analisar trechos de código, gerando respostas descritivas
    ou classificações. No experimento, o ChatGPT será utilizado com prompts
    padronizados para fornecer uma classificação binária (presença ou ausência de
    \textit{code smell}) para cada trecho de código reconstruído a partir do MLCQ.

    \item \textbf{Gemini}\footnote{Documentação em: \href{https://ai.google.dev/}{https://ai.google.dev/}. Acesso em: 6 dez. 2025.}:

    também fundamentado na arquitetura \textit{transformer}. Ele é projetado para lidar

    No experimento, o Gemini será igualmente acessado via prompts padronizados,
    produzindo uma classificação binária sobre a presença ou ausência de 
    \textit{code smell} em cada trecho avaliado.
    
    \item \textbf{Ferramentas de análise estatística}: serão utilizadas planilhas eletrônicas e scripts Python com bibliotecas como 
    \textit{pandas}\footnote{Disponível em: \href{https://pandas.pydata.org/}{https://pandas.pydata.org/}. Acesso em: 6 dez. 2025.} e

\end{itemize}

\subsection{Procedimento de aplicação desses instrumentos}

\begin{enumerate}
    \item \textbf{Leitura da instância no MLCQ.} 
    O \textbf{Dataset MLCQ} é utilizado como fonte de consulta para cada instância anotada de \textit{code smell}, tomando seus metadados como ponto de partida para a análise. A partir dos campos presentes no dataset (como \textit{link} do repositório, \textit{path}, \textit{start line} e \textit{end line}), identificam-se o arquivo em que o trecho está localizado e a região específica do código de interesse.

    \item \textbf{Recuperação do código via Git/GitHub.}
    A partir do campo \textit{link}, acessa-se a URL do repositório no \textbf{GitHub} e utiliza-se o \textbf{Git} para 
    realizar o \textit{clone} (ou atualizar um clone existente) e extrair o arquivo indicado em \textit{path}. Em seguida, o arquivo completo é carregado, e as linhas compreendidas entre \textit{start line} e \textit{end line} são apenas marcadas como referência de localização do \textit{code smell}. Ou seja, o insumo para as ferramentas de detecção é o \textbf{arquivo inteiro} em que o trecho se encontra, e não somente o fragmento delimitado pelas linhas.

    \item \textbf{Validação, registro e randomização dos tratamentos.}
    O arquivo recuperado, bem como a região correspondente ao trecho anotado, são validados. Arquivos ou anotações inconsistentes são descartados. Para os casos válidos, scripts em \textbf{Python} registram o arquivo, seus metadados e a faixa de linhas associada à instância de \textit{code smell} em uma estrutura tabular (\textit{DataFrame} do \textit{pandas}) e randomizam a ordem dos cinco tratamentos (\textbf{SonarQube}, \textbf{ChatGPT}, 
    \textbf{Gemini}, \textbf{Copilot} e \textbf{DeepSeek}) a serem aplicados, em conformidade com o \textit{Completely Randomized Design} adotado.

    \item \textbf{Aplicação do tratamento baseado em análise estática (SonarQube).}
    O arquivo de código é então submetido ao \textbf{SonarQube} e avaliado com o \textit{rule set} padrão para Java. As \textit{issues} 
    classificadas como \textit{code smells} são inspecionadas e, para aquela instância do MLCQ, registra-se uma decisão binária indicando se houve ou não detecção de \textit{code smell} na região do arquivo correspondente às linhas \textit{start line}–\textit{end line}.

    \item \textbf{Aplicação dos tratamentos baseados em LLMs.}
    Em seguida, é construído um \textit{prompt} padronizado contendo instruções em linguagem natural, o conteúdo completo do arquivo Java recuperado e a indicação da região de interesse associada à instância do MLCQ. Esse \textit{prompt} é enviado, na ordem aleatória definida, aos modelos de linguagem avaliados:
    \begin{itemize}
        \item \textbf{ChatGPT} (GPT-5.1);
        \item \textbf{Gemini} (Gemini 3 Pro);
        \item \textbf{Copilot} (GPT-5);
        \item \textbf{DeepSeek} (DeepSeek-V3.2).
    \end{itemize}
    Para cada modelo, a resposta textual é armazenada integralmente e, em etapa posterior, é processada para gerar uma classificação binária padronizada (presença ou ausência de \textit{code smell} para aquela instância), conforme o formato exigido no \textit{prompt}.

    \item \textbf{Consolidação das saídas por trecho.}
    Para cada instância anotada de \textit{code smell}, os scripts em Python consolidam, em uma única linha de um \textit{DataFrame} (\textit{pandas}), os metadados do 
    \textbf{Dataset MLCQ} (inclusive o rótulo humano) e as decisões binárias produzidas por cada tratamento (\textbf{SonarQube}, \textbf{ChatGPT}, 
    \textbf{Gemini}, \textbf{Copilot} e \textbf{DeepSeek}). A partir dessa consolidação, são derivadas variáveis auxiliares por instância, como acerto, 
    falso positivo, falso negativo e verdadeiro negativo para cada ferramenta.

    \item \textbf{Agregação por projeto e cálculo das variáveis dependentes.}
    Por fim, utilizando as \textbf{ferramentas de análise estatística} (scripts Python com \textit{pandas} e \textit{numpy}, eventualmente apoiados 
    por planilhas eletrônicas), os resultados por instância são agregados por projeto, obtendo-se, para cada tratamento, a 
    \textbf{quantidade de \textit{code smells} identificados por projeto}, variável dependente definida na Seção de Variáveis do Experimento. 
    A partir dessas distribuições, são calculadas as estatísticas descritivas (medianas, variâncias, desvios padrão) e preparados os conjuntos 
    de dados de entrada para o teste de hipóteses (Kruskal--Wallis) descrito anteriormente.
\end{enumerate}



\subsection{Validade do Experimento}

São consideradas as seguintes ameaças à validade:

\subsubsection*{Validade de Constructo}

Esta ameaça diz respeito ao grau em que as medições representam o fenômeno teórico.
O constructo “detecção de code smell” pode ser interpretado de maneira distinta por cada abordagem: 
humanos utilizam julgamento semântico; SonarQube utiliza regras sintáticas; LLMs utilizam inferência estatística. 
Essa diferença pode introduzir divergências inerentes entre os tratamentos.

\subsubsection*{Validade Interna}

Refere-se ao controle das causas que podem afetar os resultados.
A execução dos LLMs depende de versões específicas dos modelos e dos prompts utilizados. Alterações nessas versões podem afetar resultados. 
A extração incorreta de trechos do MLCQ pode introduzir erro no experimento.

\subsubsection*{Validade Externa}

Esta ameaça refere-se à generalização dos resultados.
O dataset MLCQ inclui apenas código Java open-source, o que limita a extrapolação para outras linguagens ou código fechado. 
Além disso, o estudo considera um conjunto delimitado de code smells.

\subsubsection*{Validade de Conclusão}

A comparação dos tratamentos depende da análise estatística das distribuições das variáveis dependentes. 
Testes serão adotados conforme a natureza dos dados pareados. Garantir tamanho de amostra 
suficiente por smell é fundamental para evitar conclusões inválidas.
